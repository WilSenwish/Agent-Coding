# impact-scan.md 模板（改动波及面扫描）

> 目的：在写规约之前先扫存量代码，把"人脑记不住、Agent 看不见"的影响面显性化。**先扫代码，后写规约**，否则规约必漏。
> 每条编号 `IMP-xx`，规约的每条 SPEC 必须绑定至少一条 IMP；无绑定者判"影响面漏扫"。

## 扫描方法（按顺序）

1. 从需求关键词反查代码：`Grep` 入口方法名、表名、枚举值、Redis key 前缀、MQ topic。
2. 顺着调用链向上找调用方（谁在调这个 Service/接口）、向下找依赖（它调了谁）。
3. 查历史：`git log --follow <file>`、`git blame` 关键分支，识别"为什么当初这么写"。
4. 查配置与开关：feature flag、灰度配置、定时任务、异步回调、重试策略。

## 七类必扫项

### 1. 模块与调用链
| ID | 目标 | 动作 | 风险 | 证据 |
|---|---|---|---|---|
| IMP-01 | OrderController#cancel | 修改校验 | 中 | OrderController.java:120 |
| IMP-02 | 上游调用方：小程序端 / 客服后台 | 契约变更需同步 | 高 | Grep `cancelOrder` 命中 4 处 |

### 2. 数据契约
- 入参/出参字段、类型、必填性变更？
- HTTP 状态码、错误码是否新增/复用原有？
- 是否有调用方按旧字段做解析（序列化兼容）？
- 内部 RPC / DTO 是否被多方复用？

### 3. 数据库
- 涉及表、字段、索引；是否需要 DDL。
- **老数据兼容**：存量行是否满足新约束（唯一索引、非空、枚举扩展）。
- 事务边界：新增操作是否落在同一事务；是否引入跨库/跨服务事务。
- 锁与并发：行锁范围是否扩大，是否可能死锁。

### 4. 缓存
- Redis key 结构与命名空间；是否与旧 key 冲突。
- 过期策略、脏写风险、双写一致性、缓存击穿/雪崩。
- 变更后是否需要清理存量缓存（**最容易漏**）。

### 5. 上下游与异步
- 下游接口：超时、重试、降级、幂等键。
- MQ：topic、分区键、消费幂等、消息版本升级。
- 定时任务/补偿任务：是否需要同步改逻辑。
- 外部第三方：是否需要 WireMock 场景准备。

### 6. 既有业务规则与历史分支
- 存量特殊分支（白名单、灰度、兼容老版本、历史补偿逻辑）。
- 存量边界 case（空值、超长、特殊字符、时区、金额精度）。
- **默认策略**：存量未被需求明确要求改动 → 保持原样，写入 `OUT_OF_SCOPE` 或 `OPEN`，禁止"顺手优化"。

### 7. 非功能约束
- 权限：接口鉴权、角色、数据可见范围。
- 幂等：重复提交、消息重投。
- 限流/熔断：QPS 阈值是否受影响。
- 数据脱敏与日志：新增字段是否含敏感信息。
- 观测：是否影响已有监控指标/告警规则。

## 输出分级

| 等级 | 判定 | 处置 |
|---|---|---|
| 高 | 涉及数据一致性、资金、权限、跨服务契约、老数据兼容 | 必须有对应单测或接口测试，E4 强制核对 |
| 中 | 局部逻辑变更、缓存、单服务内链路 | 必须有用例或明确豁免理由 |
| 低 | 注释、日志、内部重构 | 可豁免，需记录 |

## 自检两问

1. **反向覆盖**：每条 SPEC 都能指到 IMP？指不到的 SPEC 说明没扫到影响面。
2. **正向覆盖**：每个 IMP-高 都能指到一条测试计划用例？指不到就是高危裸奔。
